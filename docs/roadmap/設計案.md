## 3. メンバー・ログイン・権限

### 3.1 メンバー（`Member` を広げて1つの台帳にする）

内職さんとスタッフを別台帳にすると二重登録になるので、今の `Member` に列を足す。

| 追加する列 | 内容 |
|---|---|
| `email`（一意） | ログインの照合キー。内職さんは空 |
| `permission` | `president`（社長）／`staff`（スタッフ）／`part`（パート）。空＝ログイン不可（内職さん） |
| `departments` | 営業・制作・出荷（複数） |
| `roleNote` | 役割の自由文（「リーダー」「代行」→部門リーダー、「経理」→営業成績の入力可） |
| `employment` | `在籍`／`退職`（退職はログイン不可） |
| `freeeEmployeeId`・`joinedAt` | freee 人事労務から同期（§9） |
| `devAccess` | 既存の DEV 業務画面（商品・価格・顧客・受注など）を使えるか（§3.3） |

- 既存の `Member` との対応：名前で突き合わせて同じ人にまとめる（例：DEV「社長」＝神谷、「橋本」＝橋本 信子）。**廣瀬・安岡は DEV では内職、ロードマップではパート（出荷）** → 同じ方なら1人にまとめる（要確認）。

### 3.2 ログイン

- 今の Google ログインをそのまま使う（`hd=kamiya-craft.com` 限定は実装済み）。
- ログイン時にメールで `Member` を引き、**いない／退職／permission 空は入れない**。
- 毎回のリクエストでサーバーが「今の人」（メンバーID・権限・部門・リーダーか・経理か）を判定する共通関数 `getViewer()` を作り、すべての API がこれを通る。
- 社長だけは環境変数でも許可（メンバー台帳を壊しても締め出されない保険）。

### 3.3 画面の出し分け

| 画面 | 社長 | スタッフ | パート |
|---|---|---|---|
| ロードマップ（ホーム・掲示板・事業目標・私の目標） | ○ | ○ | ○ |
| 営業成績 | ○ | ○（入力は「経理」） | **✕（タブも数字も API も無し）** |
| 制作／出荷 | 両方 | 自部門のみ | 自部門のみ |
| 社長ページ | ○ | ✕ | ✕ |
| **既存の DEV 業務画面**（商品・価格・原価・顧客・受注・製造・JAN 等） | ○ | `devAccess` を付けた人だけ | `devAccess` を付けた人だけ |

- サイドバーは本人が使える画面だけ出す。URL を直接打っても、ミドルウェアと API の両方で止める。

### 3.4 秘匿の実装（「送らない」）

- API は必ずサーバー側で絞り込んでから返す。返す前に**役割ごとの整形関数**を通す（例：個人目標は状態が「確定」でなければ社長評価・社長コメントの項目そのものを消す）。
- パートには営業成績系の API を 403、ホームの API でも数字の項目を作らない。
- **自動テスト**：社長・スタッフ・パートのセッションで各 API を呼び、レスポンスに「他人の目標」「確定前の社長評価」「売上の数字」が含まれないことを確かめるスクリプトを用意（完了条件の 1・2 をこれで確認）。

### 指示書 §0.5「足りていないところ」への対応

| 足りないところ | 対応 |
|---|---|
| 営業ほか全員のタスク | `WorkLog` を部門を問わず使う。営業は「項目＝訪問・見積・提案…」で、数は任意・時間で記録。入力画面は制作／出荷と同じ形で「営業」も出す |
| 月目標の実績を自動集計 | 個人の月目標に「自動集計」の条件（項目・種別、例：口金／3.3寸）を持たせ、その月の本人の `WorkLog` 実績数を合計して表示。手入力した値があればそちらを優先（どちらを使ったかを表示） |
| 個人目標と会社の四半期目標のひも付け | 個人の四半期マイルストーンに `事業目標ID` を持たせる。事業目標の画面に「この目標を支える個人目標：○人・平均達成率」を出す。**中身（他人の目標）は社長にだけ見せ**、スタッフには人数と達成率だけ |
| 伸びの見える化 | 本人の画面に、前月比（↑12%）、自己ベスト（月の最高・1時間あたりの最高）、連続達成（月目標を○か月連続で達成）。責める表示（赤字の比較・順位）はしない。部門平均との比較は本人とリーダー・社長だけ |

## 7. 週次の取り込み（§7）

- **取り込み API**：`Authorization: Bearer <トークン>`（Vercel の環境変数に保存、社長だけが知る）。重複しないキーは指示書どおり（FLAM＝日付、Amazon入金＝入金日＋市場、広告費＝週、カード＝締め日単位で丸ごと入れ替え）。
- Cowork のスケジュールタスクの書き込み先を、スプレッドシートから「この API」に変える（移行の最後）。
- **事業計画スプレッドシートへの書き戻し（提案）**：DEV から Google Sheets API で書く。
  - DEV の Google Cloud プロジェクト（Google ログイン用に作ったもの）に**サービスアカウント**を作り、「事業計画」スプレッドシート**だけ**をそのアカウントに編集共有する（他のファイルには触れない）。
  - `syncBizPlan_` の守り（数式セルは触らない・空で上書きしない・締まった過去月は書き換えない）をそのまま移植し、書き込んだセルを記録する。
  - GAS に残す案は、DEV のデータを GAS が取りに来る仕組みが別に要るので、かえって複雑になる。

## 8. freee 人事労務との同期（§0.6）

- freee のアプリ登録（社長アカウントで1回認可）→ 毎日1回、従業員一覧から**氏名・入社日・在籍/退職**だけを取り、`Member` を更新（freee の従業員IDで照合、初回は氏名で照合して確認）。
- **給与・口座・マイナンバー等は取得しない**（そもそも API のその項目を呼ばない）。
- 退職になったらログイン不可。権限・部門・役割・メールは DEV 側で持つ。
- 時期：段階2は移行データのメンバーで動かし、freee 同期は段階2の後半（アプリ登録が済んだら）。

## 9. 移行手順

1. **データは repo に入れない**：移行データは repo の外（例：`~/roadmap-data/`）に置き、スクリプトにパスを渡す。念のため `.gitignore` にも `roadmap-data/` を追加。
2. スクリプト `scripts/roadmap/import_*.mts`（何度流しても重複しない upsert）：
   - メンバー＝メール、個人目標・事業目標・月目標・作業実績＝GAS版のID、カレンダー＝開始日＋タイトル、営業成績＝§7のキー、カード＝締め日で入れ替え、設定＝キー。
   - まず「書き込まずに件数だけ出す」モードで確認 → 本番に書く。
   - 最後に**件数照合レポート**（GAS版の件数と DEV の件数、カードの締めごとの件数・合計）を出す。完了条件の「10/21締め 188件・1,293,041円／11/21締め 32件・347,775円」をここで確認。
3. 段階ごとに、その段階で使うデータだけ先に入れて動かす（段階2＝メンバー・個人目標・事業目標）。
4. **本移行**：GAS版に「○日○時から入力停止」を告知 → 最新データで書き出し直し → スクリプトを流す → 件数照合 → スタッフに新しい URL（DEV の `/roadmap`）を案内 → スケジュールタスクの書き込み先を切り替え → GAS版を止める。
