# 本番DBの復元手順

毎日 3:00（日本時間）に GitHub Actions「DB backup」（`.github/workflows/db-backup.yml`）が本番 Turso DB を丸ごと書き出し、暗号化して 30 日分保存している。

- 中身: `dev-db-YYYYMMDD-HHMM.sql.gz.gpg`（SQL を gzip → AES256 で暗号化）
- 場所: GitHub → Actions → DB backup → 各実行の「Artifacts」
- 書き出しのたびに、空の DB に流し込んで「壊れていない・件数が一致する」ことを確かめてから保存している（失敗した日は実行が赤くなり、GitHub から通知メールが届く）

> Turso 自体にも自動のスナップショット（ポイントインタイム復元）がある。数日以内の事故ならまず Turso の管理画面で戻せないか確認し、それで足りない時やTurso側の障害の時にこの手順を使う。

## 0. 用意するもの

- `BACKUP_PASSPHRASE`（暗号化のパスフレーズ。GitHub の Secrets からは読み出せないので、社長が別に保管しているもの）
- `gpg`（Mac: `brew install gnupg`）、`sqlite3`（Mac は最初から入っている）
- Turso CLI（`brew install tursodatabase/tap/turso` → `turso auth login`）

## 1. バックアップを取ってくる

GitHub の Actions → DB backup → 戻したい日の実行 → Artifacts からダウンロードして解凍する（zip の中に `.sql.gz.gpg` が1つ入っている）。

## 2. 復号して SQL に戻す

```sh
gpg -d dev-db-YYYYMMDD-HHMM.sql.gz.gpg > dump.sql.gz   # パスフレーズを聞かれる
gunzip dump.sql.gz                                      # → dump.sql
```

中身を確かめるだけなら手元の SQLite に入れて見られる（本番には触れない）:

```sh
sqlite3 restored.db < dump.sql
sqlite3 restored.db "SELECT COUNT(*) FROM \"Product\";"
```

## 3-A. 全部を戻す（新しい DB を作って切り替える）

本番 DB は上書きしない。新しい DB を作って、アプリの接続先を切り替える（元の DB は調査用に残る）。

```sh
turso db create dev-restore-YYYYMMDD --from-dump dump.sql
turso db show dev-restore-YYYYMMDD --url                 # → libsql://...
turso db tokens create dev-restore-YYYYMMDD              # → 読み書きトークン
```

1. Vercel → プロジェクト → Settings → Environment Variables の `TURSO_DATABASE_URL` と `TURSO_AUTH_TOKEN` を新しい値に変える
2. Deployments から最新を Redeploy（環境変数は再デプロイで反映される）
3. https://dev.kamiya-craft.com で中身を確認
4. GitHub の Secrets `TURSO_DATABASE_URL` / `TURSO_AUTH_TOKEN`（バックアップ用・読み取り専用）も新しい DB に向け直す。忘れると古い DB を取り続ける
5. ローカルの `.env` も同様に直す

## 3-B. 一部だけ戻す（消してしまった行・テーブルだけ）

2 で作った `restored.db` から必要な行を取り出し、本番に入れ直す。本番に書く前に、対象を CLAUDE.md の手順どおりバックアップしてから行う。

```sh
# 例: 消してしまった顧客1件を INSERT 文として取り出す
sqlite3 restored.db ".mode insert Contact" "SELECT * FROM \"Contact\" WHERE id = 'xxx';" > fix.sql
turso db shell <本番DB名> < fix.sql
```

## 手動でいますぐバックアップを取る

GitHub → Actions → DB backup → Run workflow。大きな変更（スキーマ変更・一括更新）の前に押しておくとよい。

手元に取るだけなら:

```sh
node --env-file=.env scripts/backup_dump.mjs backup.sql counts.json
python3 scripts/backup_verify.py backup.sql counts.json
```

## 注意

- GitHub は、リポジトリに 60 日間コミットがないと定期実行を自動で止める。止まったら Actions 画面の「Enable workflow」で戻す
- パスフレーズを無くすと全バックアップが開けなくなる。パスワードマネージャー等に保管する
- このリポジトリは公開なので、成果物は暗号化したファイルだけにしている。復号した `dump.sql` をリポジトリに入れたり、共有ドライブに置いたりしない
